# Test ID Requests

Elements we can't reliably target by visible text, ARIA role, or label. Each row is a small ask for the dev — adding the suggested `data-testid` makes the matching Page Object more robust to copy/layout changes. Not a blocker: tests ship with a best-effort selector (noted below) and get tightened once the id lands.

| Page | Element | Why it's hard to target | Current selector (best-effort) | Suggested `data-testid` |
|------|---------|---------------------------|----------------------------------|---------------------------|
| Storefront header | Account menu button shown after a customer signs in (replaces the "Sign in" button) | No visible text and no `aria-label` once signed in | `header button[aria-haspopup="menu"]` (relies on the Radix dropdown-trigger attribute, not a stable id) | `account-menu-button` |
| Storefront header | Region/currency toggle button (shows current currency code, e.g. "USD"/"KWD") | No stable accessible name beyond the currency code text, which changes | `getByRole('button', { name: /USD\|KWD/ })` scoped to `header` | `region-toggle-button` |
| Storefront checkout | Payment Method radio inputs | Labels depend on which payment methods the backend returns — currently broken (returns none), so a live-verified selector only exists for "Cash on Delivery"; scoping to the "Payment Method" section is required because an unscoped label match false-matches the unrelated "Coupon Code" label elsewhere on the page (`/COD/i` matches the substring "Cod" inside "Code") | `page.getByRole('heading', { name: 'Payment Method' }).locator('xpath=..').locator('label', { hasText: /cash on delivery\|COD/i })` (see `storefront-checkout.page.ts`'s `selectCashOnDelivery()`) | `payment-method-cod` |
| Storefront checkout | Area `<select>` in the Shipping Address form | No `aria-label`, `name`, or associated `<label for>` — "Select area" is only the text of the placeholder `<option>`, not the element's accessible name, so `getByRole('combobox', { name: 'Select area' })` matches nothing | `getByRole('combobox')` (only one combobox on the checkout page at this point in the flow, so unscoped works but is fragile if a second one is added) | `checkout-area-select` |
| Admin order detail | Edit (pencil) button next to "Customer Information" | No accessible name, icon-only | `heading:has-text("Customer Information") + button` (positional) | `edit-customer-info-button` |
| Admin order detail | Edit (pencil) button next to "Shipping Address" | No accessible name, icon-only | `heading:has-text("Shipping Address") + button` (positional) | `edit-shipping-address-button` |
| Admin orders list | Per-row "..." action button (opens the "Order Details"/"Assign Driver"/etc. menu) | No accessible name, icon-only, and it's the only button in its `<tr>` | `row.getByRole('button').last()` (positional; happens to be unambiguous only because it's the row's sole button) | `order-row-actions-button` |
| Admin products list | Per-row "..." action button (opens the "View"/"Edit"/"Copy ID" menu) | No accessible name, icon-only, and it's the only button in its `<tr>` | `row.getByRole('button').last()` (positional; happens to be unambiguous only because it's the row's sole button) | `product-row-actions-button` |
| Admin order detail | "Add item" dialog's own submit button, vs. the page-level trigger button that opens it | Both buttons share the exact same accessible name ("Add item") — a real accessibility gap, not just a hard-to-target element. Confirmed live during Task 6/line-item-editing investigation. Currently safe only because the dialog's submit button is always scoped to the dialog (`dialog.getByRole('button', { name: 'Add item', exact: true })`) rather than matched unscoped | `dialog.getByRole('button', { name: 'Add item', exact: true })` (relies on remembering to scope every call site to `dialog`, not a structural guarantee) | `add-item-submit-button` (on the dialog's own submit button, to disambiguate its name from the trigger) |
| Admin order detail | Inline line-item editor's "Save"/"Cancel" (checkmark/X) buttons, shown in place of a row's "Edit"/"Delete" buttons after clicking "Edit" | No accessible name at all — no `title`, no `aria-label`, no visible text, and their `<svg>` icons have no `<title>` child either (confirmed live via full attribute inspection). Unlike the row's own "Edit"/"Delete" buttons (which DO resolve names via a `title` attribute), these two genuinely have none | `row.locator('button:has(svg.lucide-save)')` / `row.locator('button:has(svg.lucide-x)')` (relies on the third-party Lucide icon library's own CSS class names, not an app-owned identifier) | `line-item-save-button` / `line-item-cancel-button` |
| Storefront header | Cart button (opens the mini-cart) | Its accessible name is unstable: it's `<button title="Cart">` with an icon, but once the cart is non-empty a count-badge `<span>` is rendered inside it — subtree text content outranks the `title` attribute in accessible-name computation, so the button's accessible name silently becomes the badge digits (e.g. `"1"`) instead of `"Cart"` as soon as anything is added. Confirmed live: `getByRole('button', { name: 'Cart' })` matches only while the cart is empty and breaks the moment it isn't. Also confirmed live that the badge itself is a distinct-line-item count, not a total-units count — adding an already-in-cart product again leaves the badge unchanged while that line's own `quantity` increments | `button[title="Cart"]` (matches on the `title` attribute directly, sidestepping the accessible-name instability — but still says nothing reliable about cart contents, which `checkout.flow.ts`'s `placeOrder()` instead verifies via the `POST /api/cart/items` response body) | `cart-button` |
| Admin Suppliers page | "Add supplier" dialog's own name input | No `aria-label`/`for` confirmed live to tie a `<label>` to it — it's just the dialog's first plain textbox | `dialog.getByRole('textbox').first()` (positional; safe only because this dialog currently has exactly one textbox) | `supplier-name-input` |
| Storefront Supplier Portal | Per-row editable supplier-stock number input | Multiple numeric inputs likely render per stock row (e.g. a read-only "own stock" figure alongside the editable "supplier stock" one); no accessible name distinguishes them from each other | `row.getByRole('spinbutton').last()` (positional; unconfirmed live — no supplier test credentials available yet, see the Task 6 blocker note) | `supplier-stock-input` |
| Admin product edit form | "Contact Lens" and "Toric / Astigmatism" toggle switches | No accessible name at all, confirmed via a full accessibility-tree dump — unlike most switches on this form (e.g. "Allow pre-order", which resolves fine via `getByLabel`), neither the adjacent heading nor paragraph text is wired up via `aria-labelledby`/`<label for>` for these two | `contactLensSection().getByRole('switch').nth(0)` / `.nth(1)` (positional within a scoped container, ordering confirmed live but not guaranteed by any DOM contract) | `contact-lens-toggle` / `toric-astigmatism-toggle` |
